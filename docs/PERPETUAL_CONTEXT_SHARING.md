# 十几亿 Token：永续上下文的普通一天

> 当 Cache 读取免费以后，我们是不是应该重新想象 Agent 的记忆？

> 图：一天内的真实 AI 用量。不是压力测试，也不是为了这篇文章专门跑出来的数据。

这一天，我调用了很多次 AI，也用了很多个不同的模型。用量页面上累积出来的 Token，最后超过了十亿。

第一次看到这个数字，很容易怀疑我是不是在做什么极限测试。其实没有。这只是我平时使用 AI 很普通的一天：让 Agent 读消息、调工具、继续没做完的事情；我自己也会写代码、查资料，偶尔把同一个问题交给不同模型。

十几亿 Token 听起来很吓人。如果它们全部按照普通输入重新计费，这种用法当然不可持续。可真正有意思的地方恰恰在这里：图上的十几亿，并不等于十几亿 Token 都是新内容，也不等于模型把十几亿 Token 从头计算了一遍。

其中很大一部分，只是同一段过去被再次带回了当前回合。

## 61 万 Token，真正没命中缓存的只有 771

下面是我的 Agent 在一段日常运行记录中，输入规模最大的一次调用：

```text
本轮输入：610,435 tokens
命中缓存：609,664 tokens
模型输出：236 tokens
```

缓存命中率大约是 99.87%。从输入构成看，超过 61 万 Token 的上下文里，真正没有命中缓存的只有 771 Token。

我后来又从本地日志里单独抽出过一段日常运行记录：2026 年 8 月 26 日 13:42 到 23:59，LongCat-2.0 一共完成了 2,042 次调用，总输入流量约 4.76 亿 Token，其中约 4.72 亿是缓存读取，占 99.28%。这还不是完整的一天，也不能代替开头那张跨模型统计图，但它至少说明，十亿级上下文并不是靠某一次异常大请求堆出来的。

这正是 Prompt Cache 改变的事情。

一个长期工作的 Agent，每轮输入通常不是完全不同的。System Prompt、工具定义和过去的对话都在前面稳定地排列着，真正变化的主要是末尾新发生的几句话、几个工具结果。只要前缀没有变化，模型服务就有机会直接复用已经处理过的部分。

```text
过去的长历史  P ───────────────┐
本轮新增内容  N                 ├─ 本轮请求：P + N
                                │
下轮继续新增  N2 ───────────────┴─ 下轮请求：P + N + N2
```

在我当时使用的两条线路里——Claude Code 订阅制的逆向接入，以及我当时使用的 LongCat 线路——缓存读取没有产生额外的现金费用。Claude Code 订阅制的情况后来也有了更明确的官方说明：套餐内使用一小时缓存不会额外按 Token 计费；如果套餐额度已经用完并开始使用 usage credits，规则则会发生变化。[Claude Code Prompt Caching](https://code.claude.com/docs/en/prompt-caching)

这里需要把话说准确。免费来自具体的订阅、线路和计费方式，不是“所有模型的 Cache 永远免费”。例如 OpenAI 当前多个模型的 cached input 价格是普通 input 的十分之一；LongCat 当前公开的按量付费页面也已经单独列出了 cached input 价格。[OpenAI Models](https://developers.openai.com/api/docs/models/compare)、[LongCat-2.0 定价](https://longcat.chat/platform/docs/zh/pricing/long-cat-2.0)

但即使不是完全免费，方向也很明显：稳定历史正在从一段每轮重复付费的输入，变成一种可以反复复用的计算资产。

这也是十几亿 Token 能够成为日常的原因。账面上经过模型接口的上下文规模可以非常大，真正决定边际成本的，却越来越接近这一轮新增了多少内容、写入了多少新缓存，以及模型输出了多少。

## 有时候，什么都不做反而更贵

Prompt Cache 通常有有效期。Agent 一直活跃时，每次调用会自然地保持缓存温热；真正麻烦的是夜间、等待外部结果或者一段时间没有新任务的时候。

如果我判断它很快还会继续工作，就可以在缓存即将过期前，发起一次很小的保温请求：

```text
稳定历史 P + 临时保温消息 H
稳定历史 P + 下一次真实任务 N
```

只要两次请求共享完全相同的稳定前缀 `P`，缓存断点也落在正确的位置，下一次真实任务就仍然可以复用这段历史。那句保温消息不需要进入 Agent 的正式经历，它更像运行层的一次“呼吸”。

这会产生一个很反直觉的结果：一次看起来没有实际产出的微小调用，可能比什么都不做更便宜。它付出少量新增输入和请求额度，换来的却是下一次不必重新建立几十万 Token 的缓存。

当然，不是每个 Agent 都值得这样保温。一个月才用一次的 Agent，大可以让 Cache 自然过期。真正值得保温的，是那些上下文很长、近期还会被再次唤醒，而且缓存重建明显更贵的角色。

从这个角度看，未来的 Agent 不只会管理任务，也会开始管理自己的认知成本：什么时候保持专注，什么时候整理记忆，什么时候彻底休息。

不过，如果故事停在这里，它仍然只是一种 Token 优化。Cache 只是让一段过去更便宜，不能自动告诉 Agent 哪些事情值得留下，更不能让它因为经历过一次失败，就在下一次做得更好。

## 我说的“永续”，不是让模型永远运行

“永续上下文”这个名字很容易让人想到一个永不停止、24 小时持续烧 Token 的模型。那不是我想做的东西。

Agent 大部分时间完全可以休眠。只有消息到来、定时器触发、后台任务完成，或者它确实还有事情要推进时，才需要再次调用模型。

永续的不是推理进程，而是它的经历。

一次任务结束后，Agent 不会因为 Session 被关闭就突然变成第一天上班；进程重启以后，也不会把昨天做过的决定当成从未发生。任务只是同一条时间线上的一个片段，而不是它全部生命的边界。

我通常用一个很简单的问题判断某个场景是否需要永续上下文：

> 如果前 100 次任务和第 101 次毫无关系，就用普通的按需 Agent。<br>
> 如果第 101 次理应因为前 100 次的经历而做得更好，那么“经历如何延续”就是产品的一部分。

## 那为什么不直接用 OpenClaw？

可以，而且很多时候应该直接用。

OpenClaw 已经提供持久 Session、Memory、Compaction、Prompt Cache、Heartbeat 和定时任务。普通 Agent 按需唤醒，也不等于它每次都必须失忆。[OpenClaw Main Session](https://docs.openclaw.ai/concepts/main-session)、[OpenClaw Memory](https://docs.openclaw.ai/concepts/memory)、[OpenClaw Prompt Caching](https://docs.openclaw.ai/reference/prompt-caching)

“什么时候运行”和“醒来后是不是回到同一段经历”，本来就是两个问题。

我选择自己做，不是因为现成框架做不到持久化，而是因为这次实验的对象正好就是持久化本身：什么应该进入同一条时间线，什么时候应该压缩，哪些经历值得成为长期记忆，一次失败又应该怎样改变下一次行为。这些事情当然也可以通过定制现成框架来研究，并不要求每个人都从零造一个 Agent。

所以这里真正想讨论的不是框架之争，而是一个产品判断：当长上下文越来越可用、Cache 又把成本大幅压低以后，我们是不是应该让一部分 Agent 从“完成一次任务的工具”，变成“能够积累经历的角色”？

如果把这件事说得再简单一点，我想解决的其实是三个问题：先让它**用得起**，再让它**接得上**，最后看它能不能**长得大**。

用得起，靠的是 Cache 对稳定历史的复用；接得上，靠的是 Context 保留连续、高保真的工作现场；长得大，则要靠长期 Memory、技能、工具和真实反馈，把经历逐渐变成下一次可以复用的能力。

## Context 是短期工作记忆，Memory 是长期记忆

说到 Agent 的记忆，很多人首先想到的是向量数据库、用户画像和 RAG。这些当然有用，但一个正在做事的 Agent，最先需要的往往不是一条跨越半年的事实，而是一段不会轻易断掉的工作现场。

比如，我们刚才为什么排除了方案 A？方案 B 是正式决定，还是为了赶时间的权宜之计？哪个工具调用失败了？失败以后又验证了什么？用户说“还是换回前一个”，指的到底是哪一个版本？

这些内容未必值得永久保存，却对接下来的十几轮、几十轮至关重要。它们的价值不只是事实本身，还包括发生的顺序、当时的语气、前后的因果，以及哪些判断后来已经失效。

我喜欢这样区分：

> Context 保留现场，Memory 保存跨越现场仍然有价值的东西。

长期 Memory 可以记住“团队最后选择了方案 B”。完整 Context 却还知道：选择 B 时依赖了什么假设，为什么临时排除了 A，以及三天后的测试是否已经推翻了当时的前提。

只用 Context 不行。历史会越来越长，噪声越来越多，迟早碰到窗口上限。只用长期 Memory 也不行。任何提炼都会丢失细节，任何检索都有可能漏掉关键内容，而且一条孤立结论很容易失去它原本的条件。

更好的方式，是让长短期记忆形成循环：

```text
长期 Memory
    ↓ 召回相关经验
短期 Context
    ↓ 行动、结果与反馈
产生新的经历
    ↓ 筛选、纠错和沉淀
长期 Memory
```

Context 负责让 Agent 接得上，Memory 负责让重要经验留得久，Cache 则负责让活跃 Context 养得起。

长期记忆也不只有一种。稳定事实可以进入语义记忆；某次失败为什么发生，可以成为情节记忆；反复验证有效的方法，可以逐渐沉淀成技能；哪些判断最容易出错、什么情况下必须额外验证，则会慢慢形成它对自己的认识。

游戏 Agent 和项目 Agent 需要的记忆完全不同，需要的工具也完全不同。游戏 Agent 要读取状态、执行操作、分析回放；项目 Agent 要理解文档、代码、任务和历史决定。这也是我愿意自己做 Agent 的原因之一：不必一开始接受一套包办所有场景的“通用记忆”，而是可以观察真实需求，再给它增加最小、最合适的长期记忆、Notebook、技能和领域工具。

## 记得很多，不等于真的会成长

一个保存了全部聊天记录的 Agent，也可能只是拥有一本越来越厚的流水账。

真正的成长必须经过反馈：它做了一件事，看到结果，知道哪里对、哪里错，然后让这次经历改变下一次选择。

```text
行动 → 结果 → 反馈 → 复盘 → 调整 → 再行动
```

如果 Agent 每次都记得自己失败，却永远重复同一种失败，那不叫经验，只能叫存档。

所以我说的“Agent 进化”，并不是模型偷偷修改了自己的权重，而是同一个模型逐渐形成了情节记忆、策略认识、可复用技能，以及对自己弱点的认识。模型没有重新训练，行为却因为经历而发生了变化。

可以把它概括成一句话：

> Cache 解决养得起，Context 解决接得上，Memory 解决记得久，反馈闭环才解决长得大。

## 我想先让它去玩《杀戮尖塔》

游戏大概是验证这件事最合适的地方。反馈明确，失败成本低，可以重复，而且“有没有进步”不必完全依赖主观感受。

我最想做的是让 Agent 连续玩《杀戮尖塔》。不是让最强模型偶然通关一次，而是做三组对照：

| 实验组 | 每局结束后保留什么 |
|---|---|
| 失忆组 | 清空经历，下一局重新开始 |
| 永续 Context 组 | 保留连续经历，但不额外提炼长期策略 |
| 长短期记忆组 | 保留当前现场，并把验证过的教训沉淀为 Memory 或技能 |

三组使用相同模型、相同游戏接口和相近预算。连续运行 50 局、100 局以后，再看它们的平均到达层数、胜率、重复错误、策略变化和成本。

我尤其想知道：它会不会因为一次偶然胜利学到错误经验？会不会在新的证据出现后主动推翻旧策略？从一个角色身上学到的东西，能不能迁移到另一个角色？

如果模型权重完全没变，长短期记忆组却逐渐成为更成熟的玩家，这就说明能力不只存在于模型参数里，也存在于一个 Agent 如何保存、修正和使用自己的经历。

《宝可梦》会是更适合讲故事的版本。“Agent 自己进化”和宝可梦进化有天然的双关，它还可以记住地图、队伍、对手，以及一起走过的旅程。不过完整 RPG 会混入视觉、导航和操作稳定性等问题。要做严肃对照，我会先选《杀戮尖塔》；要做面向大众的演示，我会选《宝可梦》。

## 放到工作里，它更像一个有工龄的员工

“超级员工”听起来很吸引人，但我不觉得未来会突然出现一个无所不能的 AI，把公司所有岗位都包办了。

我更相信另一种形态：团队里会出现一些长期存在、职责明确的 AI 员工。它们未必比临时调用的模型更聪明，却因为从项目第一天就在场，参与过讨论、妥协、上线、事故和复盘，逐渐拥有了工龄。

老员工的价值不只是读过更多文档。他知道为什么当初没有选另一套方案，某条规范是被哪次事故逼出来的，谁对哪个模块最熟，以及哪些看似确定的结论其实只是历史条件下的妥协。

AI 也可以逐渐获得这种经验。

我比较看好的结构，是先有一个项目常驻 Agent。它保存项目的连续经历、当前目标和未完成事项；遇到编码、研究、测试、设计等具体任务时，再去调用不同的模型或者短命的专家 Agent。专家完成工作以后，结果重新回到这条主时间线里。

这也解释了开头那张多模型用量图。图上有很多模型，但真正需要“永续”的不是其中任何一个模型，而是那个记得为什么调用它们、怎样评价结果、接下来还要做什么的 Agent。

> 模型提供能力，Agent 保留经历。

当然，切换模型通常不能共享同一条 Prompt Cache，甚至改变推理强度、工具定义或者前缀顺序，都可能导致 Cache miss。但持久经历不应该因此消失。最多只是换了一台发动机以后，需要重新把这段历史装载一遍。

这也是“模型决定智商，上下文决定工龄”更准确的含义。模型决定 Agent 这一刻有多聪明，连续经历决定它半年以后是不是仍然像第一天入职。

## 永续也会让错误复利

写到这里，永续上下文听起来像一件只有好处的事。但它真正危险的地方，恰恰来自“持续”。

模型能接收一百万 Token，不代表它能同样可靠地利用其中每一个位置。OpenAI 公布的 GPT-5.6 Sol 在 MRCR v2 8-needle 测试中，256K–512K 区间得分为 91.5%，到了 512K–1M 区间下降到 73.8%。这已经很强，但远远不是“放进去就一定记得，记得就一定会用”。[GPT-5.6 长上下文评测](https://openai.com/index/gpt-5-6/)

历史还会积累噪声。过期计划、错误判断、重复工具结果、闲聊，甚至外部内容里的恶意指令，都会跟着一起留下来。上下文越大，真正稀缺的东西越可能从容量变成注意力。

长期记忆也可能把偶然经验固化成偏见。一次侥幸通关，不一定能证明某套策略普遍有效；一次赶工时的妥协，也不应该被永久记成团队规范。Memory 必须能够标注来源、接受纠正、被新证据替代，而不是只会添加“重要事实”。

免费 Cache 本身也不是永恒承诺。订阅规则会变，免费额度会结束，模型升级、前缀变化和供应商切换都会让缓存失效。保温请求还会占用请求次数和套餐额度。对低频、短上下文任务来说，维护 Cache 很可能比冷启动更加浪费。

最后是隐私。一个有工龄的 AI 员工，很可能同时拥有大量人的消息、项目决策和行为记录。谁能查看，谁能纠正，哪些内容可以跨项目流动，一个人离开后相关信息怎样删除，都会成为必须回答的问题。

所以，永续绝不能被理解成永不删除。

> 不要让 Agent 无缘无故失忆，也不要让它无选择地记住一切。

## 未来的 Agent，会管理自己的记忆

尽管问题很多，我仍然觉得“永续”会成为一条明显的趋势。

它正在变得可行，不是因为某一个突然出现的突破，而是三个变量同时发生了变化：物理窗口已经来到百万 Token 级别；好模型利用数十万乃至更长上下文的能力仍在改善；Prompt Cache 也从隐藏优化，逐渐变成可以控制、可以计量的产品能力。

物理窗口回答“能不能装下”，有效上下文回答“能不能用好”，Prompt Cache 回答“能不能长期用得起”。三个问题都开始得到比过去更好的答案，产品的默认顺序也就有机会改变：过去是默认遗忘，需要时再尝试召回；未来可能是先保留仍然活跃的现场，确实遇到容量、成本或相关性压力时，再压缩和沉淀。

我猜未来的 Agent 会同时拥有几层记忆。

最热的一层是当前原始 Context。它高保真地保存工作现场，尽量利用 Cache 反复复用。再往下是阶段性经历：已经结束的任务、重要因果、未完成事项和阶段复盘。最冷的一层是长期 Memory、技能和外部资料，需要时再检索。

RAG 不会消失，但它的位置会改变。它不必再负责抢救刚刚被系统主动丢掉的现场，而更多负责访问真正离开当前工作集的旧知识。

更进一步，Agent 可能开始自己判断：这段 Context 值不值得保温，什么时候应该压缩，什么经验应该晋升为长期记忆，哪些旧结论需要纠正，切换模型是否值得付出一次冷启动，以及什么时候应该彻底结束一段时间线。

今天我们习惯把一次聊天、一次任务、一个 Session 当成 AI 产品的基本单位。未来，对某些 Agent 来说，基本单位可能会变成一个角色的一生：它参加过哪些项目，形成过什么判断，犯过哪些错误，学会了哪些技能，现在还在对什么负责。

当然，不是每个 Agent 都需要拥有“一生”。翻译一段文字、生成一份独立报告、执行一个和过去无关的脚本，都没有必要背着历史。真正适合永续上下文的，是那些经历本身会产生复利的场景。

在游戏里，这种复利表现为它不再重复送死，开始形成自己的打法；在工作里，它表现为理解一项决定的来龙去脉，也知道团队曾经为它付出过什么代价。

回头再看开头那张图，一天十几亿 Token 最值得说的并不是“我调用了很多 AI”，而是另一件事：大量、多模型、连续的 AI 调用已经成为日常，我们却仍然习惯把每次调用当成一次孤立的智力消费。

当过去能够通过 Cache 免费或者近乎免费地复用以后，Agent 终于有机会把这些孤立调用串成一段连续经历。

> Cache 让连续上下文养得起。<br>
> Context 让 Agent 保留当前现场。<br>
> Memory 让重要经验跨越任务。<br>
> 反馈和迭代，让这些记忆真正改变下一次行动。

模型决定它这一刻能想多好。工具决定它能不能真的行动。而永续上下文决定的，是它经历过的过去，能不能成为未来的一部分。

如果昨天的经历无法进入今天，再强的 Agent，也只是每天第一天上班。
